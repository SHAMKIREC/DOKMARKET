# DOKMARKET — правила для AI-агентов

## Продукт
- Главный бренд и приложение: **ДокМаркет**.
- **Досудебка** — один сервис внутри ДокМаркета. Не называй общие вход, регистрацию, кабинет, профиль, корзину или каталог «Досудебкой».
- Не трогай RB и NRV DIGITAL. Этот репозиторий — только DOKMARKET.
- Интерфейс должен быть понятен человеку без юридической и технической подготовки.

## Как работать
1. Сначала прочитай связанные файлы и существующую реализацию. Не переписывай рабочий код только ради другого стиля.
2. Для локальной правки делай локальную правку. Для архитектурной задачи сначала проверь связанные маршруты, данные и состояния.
3. Не создавай декоративные кнопки. Каждая видимая кнопка должна вести к рабочему действию, честному демо или явно обозначенному недоступному состоянию.
4. Не придумывай отзывы, рейтинги, специалистов, даты юридической проверки, версии документов, количество продаж или другие факты. Демо помечай как демо.
5. Не подставляй фиктивную «актуальность» документа. Дата проверки показывается только если она есть в данных и подтверждена.
6. Mobile-first: основной текст и действия должны читаться и нажиматься на телефоне без масштабирования.
7. Не меняй юридический смысл шаблонов ради красивого текста. UI-текст и юридический документ — разные слои.
8. Не начинай широкое исследование всего репозитория, если задача указывает конкретный симптом и место. Сначала проверь указанное место и ближайшие зависимости.
9. Не добавляй новые зависимости и абстракции без необходимости. Если задача требует выйти за заданные границы, сначала объясни зачем и дождись разрешения.

## Контракт задачи
Хорошая задача для агента содержит пять частей. Если часть уже очевидна из контекста, не требуй повторять её формально.

1. **Цель** — наблюдаемый симптом или нужный результат.
2. **Место** — файл, папка, функция или существующий экран-образец, с которого начать.
3. **Границы** — что нельзя менять: соседние модули, зависимости, API, дизайн или данные.
4. **Готово** — проверяемый сигнал: тест, typecheck, build, lint, скриншот, конкретный маршрут или состояние UI.
5. **Формат результата** — коротко перечислить изменённые файлы и показать фактический результат проверок. Не заменять доказательство фразой «всё работает».

Для исправления бага сначала воспроизведи симптом тестом или другим доступным проверяемым способом, если это разумно для данного участка. Для визуальной задачи не объявляй результат идеальным только по факту изменения CSS: если среда умеет открыть страницу/сделать скриншот, проверь отрисовку.

Не добавляй в промпты ролевые украшения, обещания награды, угрозы, капс ради важности и просьбы «думай пошагово». Они не заменяют контекст, границы и проверку. Не требуй строгий JSON от агента без необходимости; для машинного интерфейса форматируй итог отдельным шагом.

## Трёхагентная петля качества
Для любой нетривиальной фичи, исправления или рефакторинга используй исполняемую петлю из `scripts/agent-loop.mjs`.

Запуск из корня проекта:

```bash
npm run agents -- --task "Описание фичи или бага"
```

Или с задачей из файла:

```bash
npm run agents -- --task-file docs/tasks/feature.md
```

Скрипт сам запускает три независимых процесса Codex: Builder с `workspace-write`, Reviewer и Auditor с `read-only`. Каждый вызов Reviewer/Auditor — новый процесс и чистый контекст. Они не получают оценки прошлых кругов. Если минимальная из шести оценок ниже 9, замечания возвращаются только Builder и запускается следующий круг. Максимум — 5 кругов. Автокоммита и автопуша нет: итоговый diff остаётся в рабочем дереве для проверки.

Если Codex CLI называется иначе, передай путь через `CODEX_BIN`. Если надо зафиксировать поддерживаемую модель, используй `AGENT_LOOP_MODEL`. Не коммить токены и секреты ради запуска петли.

### Агент 1 — Builder
Builder — единственный агент, который меняет код.

Его задача:
1. Реализовать текущую фичу минимально достаточными изменениями.
2. Не трогать соседние модули без необходимости.
3. Не добавлять зависимость, если задача решается текущим стеком.
4. Проверить изменённую часть доступным внешним сигналом: тестом, сборкой, typecheck, lint, запросом к API, чтением схемы, скриншотом или другим подходящим способом.
5. Коротко отчитаться: какие файлы изменены, что теперь работает, какие ограничения остались.

### Агент 2 — Reviewer
Reviewer получает только:
- формулировку текущей задачи;
- актуальный diff текущего круга.

Reviewer не получает оценки и замечания прошлых кругов и код не меняет.

Он обязан поставить оценки от 1 до 10 по трём осям:
- **корректность**;
- **простота**;
- **риски**.

Каждая реальная проблема должна содержать:
- файл;
- строку или минимальный диапазон строк;
- конкретную проблему;
- что именно сломается или какой пользовательский сценарий пострадает;
- минимальное исправление.

Не считать блокирующими вкусовые замечания, переименования без выгоды, абстракции ради абстракции и «можно сделать красивее», если это не влияет на пользователя, данные, безопасность, деньги, поддержку или стоимость разработки.

Оценку 9 или 10 обосновывать тем, что фактически проверено. Фразы «замечаний нет» недостаточно.

### Агент 3 — Auditor
Auditor получает ту же задачу и тот же актуальный diff, но не видит вывод Reviewer и прошлые оценки. Код не меняет.

Он обязан:
1. Провести независимое ревью с нуля.
2. Поставить свои оценки 1–10 по корректности, простоте и рискам.
3. Найти пропущенные Reviewer проблемы.
4. Отсеять придирки, за исправление которых пользователь не получает практической ценности.
5. Для каждой подтверждённой проблемы указать файл, строку, последствие и минимальную правку.

### Оценка круга
Оценка круга = минимальная из всех шести оценок Reviewer и Auditor.

Если минимум **9 или выше**:
- круг считается пройденным;
- Builder не делает косметические правки «на всякий случай»;
- итоговый отчёт перечисляет, что реально проверено и почему фича готова.

Если минимум **ниже 9**:
- Builder получает объединённый список только подтверждённых практических проблем;
- исправляет их;
- начинается новый круг;
- Reviewer и Auditor нового круга снова получают только новую задачу и новый diff с чистого контекста.

После **пятого круга** остановиться независимо от оценки и сообщить:
- минимальную итоговую оценку;
- какие проблемы остались;
- почему они не закрыты;
- что конкретно нужно для следующего шага.

### Когда петля обязательна
Полный цикл обязателен, если задача затрагивает хотя бы одно из следующего:
- оплату, заказ, корзину, выдачу купленного файла или расчёт с продавцом;
- авторизацию, роли, RLS, Storage или Edge Functions;
- создание, редактирование, публикацию или модерацию товара;
- профиль продавца, отзывы или рейтинг;
- значимый мобильный UX или ключевую навигацию;
- миграцию базы данных;
- новый публичный API или изменение существующего контракта.

Для опечатки, простого текста, одной безопасной иконки или локального CSS-отступа полный цикл не нужен.

## UI-источники
Перед новым крупным визуальным паттерном прочитай `docs/ui-sources.md`.

Общие правила:
- UI-источник — референс или исходный компонент, а не новая дизайн-система;
- итог должен использовать текущие токены и визуальный язык ДокМаркета;
- не копировать чужой бренд, тексты и айдентику;
- перед production проверять лицензию конкретного ассета;
- не ставить библиотеку целиком ради одной кнопки или карточки;
- мобильную версию проверять в первую очередь на ширинах 360–430 px;
- не смешивать стили разных источников на одном экране без унификации;
- если новый компонент визуально выглядит как «вставка с другого сайта», сначала адаптировать его к ДокМаркету.

## Текст интерфейса
Следуй `docs/content-style-ru.md`.
- Пиши действие и результат: «Заполните данные — получите документ».
- Убирай канцелярит, рекламную воду, клише, пустые абстракции и искусственные антитезы.
- Не используй «единая экосистема», «революционное решение», «в современном мире», «стоит отметить», «осуществить оплату» и похожие обороты без необходимости.
- Не обещай юридический результат, который продукт не гарантирует.
- После изменения пользовательского текста проверяй `npm run lint:copy`.

## Проверки перед публикацией
Для обычной правки запускай только проверки, которые относятся к изменённой части. Перед merge/release — полный набор:
- `npm run lint`
- `npm run typecheck`
- `npm run lint:copy`
- `npm run build`

Если проверка упала из-за старой несвязанной ошибки, не маскируй её: укажи файл и ошибку отдельно.

## Уровень рассуждения агента
Если среда/модель поддерживает настраиваемый reasoning effort, выбирай его по задаче, а не «максимум всегда»:
- **low** — переименование, простой CSS, очевидная локальная правка текста.
- **medium** — обычный компонент, форма, небольшой баг, CRUD без сложных связей.
- **high** — несколько связанных экранов, auth, Supabase/RLS, платежи, генерация документов, миграции, сложный баг.
- **xhigh/max** — только если модель это поддерживает и задача действительно требует глубокого архитектурного/безопасностного анализа или предыдущий проход пропустил важную связь.

Не переключай уровень посреди длинной задачи без причины. Если конкретная среда не поддерживает эти названия уровней, не имитируй их и не добавляй фиктивные настройки.

## Безопасность
- Никогда не коммить секреты, service-role keys, пароли или токены.
- Клиент не должен получать Supabase service-role key.
- Для новых таблиц с пользовательскими данными сначала проектируй RLS, затем UI.
- Любая операция заказа, платежа, доступа к купленному файлу или персональным данным должна проверять пользователя на серверной стороне/через RLS, а не только скрывать кнопку в React.
