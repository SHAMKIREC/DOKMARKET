# ДокМаркет — аудит и план доведения продукта

Дата: 2026-09-16

## 1. Зафиксированная продуктовая модель

ДокМаркет — единое приложение, где пользователь:
1. находит и покупает готовые документы;
2. использует внутренние сервисы (в первую очередь «Досудебка»);
3. находит специалистов и заказывает услуги;
4. хранит покупки, заказы и избранное в одном аккаунте.

«Досудебка» — сервис внутри ДокМаркета, а не отдельный общий бренд.

Терминология публичного интерфейса: **специалист**, **автор**, **эксперт**, **партнёр** — по контексту. В покупательском интерфейсе не использовать внутренние marketplace-термины «селлер» и «продавец» как название человека/раздела. Управление публикацией документов выносится в кабинет автора/специалиста и не рекламируется отдельным большим блоком на главной.

## 2. UX-аудит по текущей мобильной версии

### P0 — навигация и смысл
- Карточка категории обязана открывать каталог, уже отфильтрованный по выбранной категории. Нельзя вести пользователя в общий каталог без сохранения `category`.
- «Все категории» открывает общий каталог документов; конкретная карточка — конкретную категорию.
- «Специалисты» должны быть отдельным пользовательским сценарием, а не псевдокатегорией документов.
- Убрать с главной большой промоблок «Стать продавцом / первые продавцы проходят модерацию». Вход для автора/специалиста допустим внутри профиля/меню.
- Не смешивать документы, сервисы и специалистов в одной таксономии.

### P0 — честность данных
- Не показывать вымышленные рейтинги, отзывы, количество продаж, специалистов или «проверено», если данных нет в БД.
- Fallback-карточки должны вести в реальный поиск/сервис и не изображать совершённую покупку или существующий товар.
- Платёжные экраны должны явно различать production-оплату и неподключённое состояние.

### P1 — главная
- Сохранить утверждённый визуальный язык: тёмный фон, золото, объёмные тематические изображения категорий.
- Верх главной строить от задачи пользователя: поиск → быстрый выбор → категории → популярные документы → сервисы → специалисты → отзывы/партнёры.
- Категории сделать компактными и визуально различимыми; на мобильном не растягивать карточки по высоте.
- Карточки документов: изображение/превью, формат, название, реальная цена, реальный рейтинг только при наличии данных, избранное, понятный переход.
- Сервисы визуально отделить от товаров.
- Специалистов показывать только из одобренных реальных профилей. Если данных нет — нейтральное пустое состояние без фейковых людей.

### P1 — мобильный UX
- Проверить ширины 360, 390, 412 и 430 px.
- Fixed bottom-nav не должен перекрывать CTA/контент; у всех страниц должен быть достаточный нижний safe-area/padding.
- Горизонтальные полки должны иметь понятный край следующей карточки, scroll-snap и не обрезать текст.
- Не допускать заголовков под sticky-панелью (видно на текущих экранах «Досудебки»).
- Кнопки и поля: минимальная удобная зона касания, отсутствие случайных горизонтальных переполнений.

## 3. Логика каталога

Единый контракт URL:
- `/market?type=document` — все документы;
- `/market?type=document&category=contracts` — только «Договоры»;
- `/market?type=document&category=accounting` — только «Бухгалтерия»;
- поиск добавляется как `q=...` и не уничтожает выбранную категорию;
- сброс фильтра категории возвращает в `/market?type=document`.

Категория определяется стабильным slug из данных. Текстовое угадывание категории по названию допустимо только как fallback для старых данных и не должно переопределять явный `category_slug`.

## 4. Архитектурный аудит

Проверить последовательно:
- `App.jsx`, `pages.config.js`, Layout/Header/BottomNav — маршруты, guard-ы, дублирование навигации;
- `DocMarketHome.jsx`, `Market.jsx`, карточку товара — URL-контракты и состояния;
- marketplace services — catalog/cart/favorites/orders/reviews/seller-profile/auth;
- Supabase schema + RLS + Storage + Edge Functions;
- генерацию PDF/DOCX и шаблоны «Досудебки»;
- login/register/reset-password/session restoration;
- кабинет покупателя и кабинет автора/специалиста;
- корзину → заказ → оплату → выдачу файла;
- модерацию → публикацию → карточку → покупку → отзыв;
- ошибки сети, loading, empty, unauthorized, forbidden, not-found.

## 5. Безопасность и данные

Обязательные проверки:
- секреты и service-role отсутствуют во frontend и git history текущей ветки;
- RLS включён для пользовательских таблиц;
- пользователь не может менять чужие товары, заказы, отзывы, профили и файлы;
- публично читаются только опубликованные/разрешённые данные;
- Storage policy не позволяет угадывать и скачивать чужие приватные материалы;
- роль/статус модерации нельзя повысить из клиента;
- цена и состав заказа фиксируются серверно на момент оформления;
- выдача купленного файла проверяет право доступа;
- review создаётся только для допустимого завершённого заказа, если это продуктовый контракт;
- все внешние URL/файлы валидируются.

## 6. «Досудебка» внутри ДокМаркета

Проверить весь сценарий: выбор ситуации → данные → требования → приложения → предпросмотр → исправление → PDF/DOCX → сохранение в «Документы».

Отдельно:
- личная и коллективная претензия не должны смешивать состояние;
- цена и доступность тарифа берутся из одного источника;
- sticky subnav не перекрывает H1 и первый контент;
- Telegram/help не должен быть фиктивной кнопкой;
- юридический текст отделён от UI-copy;
- пользователь видит итог до сохранения;
- введённые данные не теряются при возврате на предыдущий шаг.

## 7. Визуальная цель

Утверждённый референс из текущего обсуждения считаем направлением, а не поводом рисовать новый макет. Реализация должна использовать существующий бренд ДокМаркета и реальные данные.

Ключевые признаки:
- тематические объёмные изображения категорий;
- более богатые превью документов вместо белого листа-заглушки;
- компактные отступы;
- реальные цены/рейтинги только при наличии;
- отдельные сервисы;
- реальные специалисты;
- отсутствие промоблока «про продавца» на главной;
- клик категории всегда сохраняет выбранную категорию.

## 8. План реализации

### Этап A — инвентаризация и контракты
1. Карта маршрутов и экранов.
2. Карта сущностей БД и RLS.
3. Карта пользовательских ролей и разрешений.
4. Таблица CTA: кнопка → ожидаемое действие → фактический маршрут/API → статус.
5. Список P0/P1/P2 дефектов.

### Этап B — P0
1. Исправить категорийную навигацию end-to-end.
2. Удалить публичную рекламу «продавца/селлера» и привести терминологию к продуктовой модели.
3. Устранить фальшивые/неподтверждённые данные.
4. Исправить перекрытия fixed/sticky UI.
5. Проверить auth/RLS/Storage/commerce на критические нарушения.

### Этап C — главная и каталог
1. Довести главную до утверждённого визуального направления.
2. Полные категории и корректные изображения.
3. Карточки документов и сервисов.
4. Реальные специалисты или честное empty state.
5. Поиск, фильтры, сортировка, URL-state, back-navigation.

### Этап D — commerce и кабинеты
1. Корзина.
2. Checkout/payment state.
3. Заказ и серверная фиксация цены.
4. Выдача купленного файла.
5. Избранное.
6. Покупки/документы.
7. Профиль специалиста/автора, публикация и модерация.
8. Отзывы после заказа.

### Этап E — Досудебка
Полный проход всех сценариев, документов, ошибок и mobile UX.

### Этап F — качество
Для каждого нетривиального блока использовать существующую трёхагентную петлю Builder → Reviewer → Auditor из `AGENTS.md`, минимум 9/10 либо фиксировать остаточный риск.

Перед release:
```bash
npm run lint
npm run typecheck
npm run lint:copy
npm run build
```

Плюс ручная/браузерная проверка ключевых маршрутов на 360–430 px и desktop.

## 9. Definition of Done

ДокМаркет готов к следующему релизному этапу, когда:
- каждая видимая CTA работает или честно сообщает недоступность;
- категория открывает именно свою выдачу;
- нет публичного промоблока «продавец/селлер» на главной;
- нет фейковых рейтингов/специалистов/продаж;
- auth и права проходят негативные сценарии;
- покупка не выдаёт файл без права доступа;
- «Досудебка» сохраняет данные и корректно генерирует документы;
- mobile UI не перекрывает контент;
- lint/typecheck/copy/build проходят;
- критические потоки проверены Builder/Reviewer/Auditor.
